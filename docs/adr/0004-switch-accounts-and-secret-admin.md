# Users get their own Switch accounts; `admin` stays secret

The lab got messy because anyone could log in to any Switch with the default `admin/switch`, so nobody reserved, and nobody could be held to cleaning up. We now keep the lab Switches' `admin` password secret, known only to BLab and the admins, and stored in deployment secrets rather than in the code. Users reach a Switch only through a **Switch account**: a local login named after them, with a random password. BLab creates it on Reserve for the holder and for each user the Topology is shared with, and removes it at Release before the Cleanup. (Amended by ADR 0007: with `BLAB_PROJECTS` on, for each member of the Reservation's Project instead, and removed when they leave it.) Backbones keep their current credentials for now.

## Considered options

- **RADIUS/TACACS behind BLab.** Rejected: too much infrastructure for a lab, and BLab's own access would depend on it.
- **BLab sets a new `admin` password for each Reservation and gives it to the holder.** Rejected: a holder who changes it locks BLab out, so the Switch can no longer be Cleaned up, and the command log shows `admin` instead of a person.

## Consequences

- Cleanup doesn't touch the local user table, because it lives outside `working/`. Removing Switch accounts is a separate step of Release, and an Inspection fails if a Switch account is still there once the Switch isn't reserved.
- A holder can still lock BLab out by changing `admin` or removing SSH authentication. The Inspection after Cleanup then fails, the Switch is Quarantined in their name, and an admin recovers it at the console. There is no console server.
- The `admin` password changes on the devices only after BLab has shipped Switch accounts, so holders always have a way in.
- Scripts that hard-code `admin/switch` stop working on lab Switches.

## How it is done (#21)

- **BLab's login.** BLab logs in to lab Switches as `admin`, trying each password of `BLAB_SWITCH_ADMIN_PASSWORDS` in `.env` (comma-separated, default `switch,Switch@123`, the two passwords the lab uses today) and starting with the one that last worked on that Switch. Changing `admin` is then: put the new password first in both `.env` files, change it on the devices at any pace, and drop the old ones once every Switch has it. BLab never sends a command that changes `admin`, except once at onboarding, to give a Switch that only takes a factory password the secret one (ADR 0010), and after a reload it started that left `admin` with an older password (#87, below). Backbones log in with `BLAB_BACKBONE_USERNAME`/`BLAB_BACKBONE_PASSWORD` (default `admin`/`switch`).
- **The AOS commands**, checked on an OS6900 with AOS 8.9.107.R02: `user <name> password "<password>" read-write all` creates the account with full privileges and SSH allowed, or resets the password of an existing one; `no user <name>` removes it. AOS answers both with exit status 0 even when it refuses them, printing `ERROR: ...` (such as `ERROR: Unknown user`, or `ERROR: Command not allowed on slave` on a VC member), so BLab reads the output. (Amended by #40, below: the password is single-quoted for the Switch's shell, not double-quoted.) The user table is not in `vcboot.cfg`, so it isn't in the config an Inspection compares with init.
- **Names.** A Switch account is named after the BLab username when AOS takes it as is (1 to 63 ASCII letters, digits and `._@+-`, case-sensitive). Otherwise, and for a username that is `admin` or `default` in any case or of the form `blab-<number>`, it is `blab-<user id>`. So two users never share a name and nobody gets `admin`. BLab shows the name next to the password.
- **Passwords** are random, 16 characters, and meet AOS's default policy (upper and lower case, digit, symbol, not containing the name; no `!`, which AOS refuses). BLab stores each one in its `SwitchAccount` row so it can show it, but only to that account's user (`GET switch_accounts/`); the admin site doesn't show it. It is not encrypted: the two stages have different secret keys, and it only opens a lab Switch while the user may work on it anyway. (Amended by #40, below: with `BLAB_PROJECTS` on, the user chooses the password instead.)
- **Failures never block.** Reserve, Share and Unshare create or remove the accounts at once; the Release's Cleanup removes them before the reload. If a Switch can't be reached or refuses, the Reservation, Share or Release still stands, the row keeps the error, and the Switch worker retries every few minutes (an Out of service Switch waits until it is back in service, #72). It also creates the accounts of Reservations and Shares made through code that doesn't know about them (production before this change). Rows are saved before BLab talks to the Switch and no lock is held meanwhile, so a crash leaves a row the worker finishes.
- **The account sync has its own lock** (`SWITCH_ACCOUNTS_LOCK`), apart from the Cleanup lock of ADR 0005, so it runs whichever stage holds the Cleanup lock, including one whose older code knows nothing of Switch accounts.
- **Until `main` runs this code**, a Release or expiry through production Cleans up the old way: it doesn't remove the accounts first and its Inspection doesn't look for them. Pre-prod's worker removes them on its next pass (retried every few minutes while the Switch reloads), so a released user may keep their login for a few minutes, and Reservations made through production get their accounts the same way. This closes once `main` has Switch accounts; until then `admin` keeps working, so nobody is locked out.
- **Inspection.** On a Switch that isn't reserved, a local user named like a `SwitchAccount` row of that Switch is a Switch account left behind and fails the Inspection. Other local users (made by hand, such as `test`) are only a warning, since BLab doesn't know who made them. (Amended by ADR 0006: with `BLAB_CLEAN_STATE_MODE=enforce`, every local user but `admin` and the lab managers' extras fails the Inspection and is removed at every Cleanup.) When all an Inspection after Cleanup finds is accounts left behind, BLab failed to remove them, so the Quarantine names nobody; the worker removes them and a Re-check lifts it.

## Switch passwords chosen by users (#40)

Random passwords that users look up in BLab didn't fit how people work: they open PuTTY or MobaXterm on many Switches and want one password they know. So, with the `BLAB_PROJECTS` stage setting on, each user chooses a **Switch password** (see `CONTEXT.md`) at an onboarding step after their email, and every page waits for it, like the email: the API refuses with code `switch_password_required` (`api/permissions.py`). They can change it on the Account page. With `BLAB_PROJECTS` off (the default, and both stages until the maintenance window), nothing changes: Switch accounts keep BLab's random passwords, shown as before.

- **Rules**, checked as the user types and again by the server (`api/switch_password.py`): 8 to 30 characters, an upper and a lower case letter, a digit and a symbol, not containing the username or the Switch account name in any case, and not `Switch@123`, `switch` or `admin` in any case. Only printable ASCII without spaces, `!`, `"` or `'`: on 10.69.144.132 (AOS 8.10.86.R04, 2026-10-12) AOS refuses spaces, `!` and more than 30 characters, and takes a quote but the password then doesn't log in. Every other symbol logs in.
- **Encrypted, not hashed.** BLab has to push it to Switch accounts made later, while the user is away, so it keeps it encrypted (Fernet, from `cryptography`) in a `SwitchPassword` row. The key is `BLAB_SWITCH_PASSWORD_KEY` in `.env`, the same in both stages, because either stage's Switch worker may push it; startup stops if `BLAB_PROJECTS` is on without a valid key, and a stage with it off needs none. Several comma-separated keys let it change: the first encrypts, all decrypt. A password no key opens is logged and left out, so that user's new accounts get a random password, shown as before, until they choose theirs again. It is never shown again, to the user or on the admin site.
- **The push.** Saving it sets it at once on every Switch account the user has (the same `user <name> password ...` command, which resets the password of an existing account). Each `SwitchAccount` records which Switch password it was last given (`switch_password_at`, the choice's time); one without the latest is out of step, so the Switch worker's retry pass gives it, and a password chosen while an older one was still being pushed gets there too. New Switch accounts are created with it. The row's random `password` is still filled in, so that `main`'s older code, if it ever syncs the row, sets a working password rather than an empty one.
- **The command goes through a shell** on the Switch, so the password is single-quoted (`shlex.quote`): `$`, backticks and backslashes otherwise change it.
- **AOS's password history.** AOS refuses a password the account had among its last four (`ERROR: New password can not be the same as your current password or any of your previous 3 passwords`), so a user going back to an older Switch password, or saving the same one again, would be refused. BLab then removes the account and creates it afresh, which clears the history (checked on 132). Should the second creation fail, the account is missing until the Switch worker's next retry.
- **Not in the Switch's logs.** AOS's CLI command log (`swlog`, `/flash/command.log`) shows the command as `user <name> password ****** read-write all` (checked on 132), so other users of the Switch can't read it there.

## Switch accounts on a Virtual Chassis (#60)

In a VC, the master holds the local users of every chassis, and a slave refuses `user` with `ERROR: Command not allowed on slave`. BLab used to retry that refusal forever. A worse problem was that an account lived only in the master's running config, so after a takeover the new master didn't have it and the user was locked out of their own VC.

- **Saved after every change.** After the `user …` and `no user …` commands of a sync, BLab runs `write memory` once on that Switch, not once per account. AOS then copies the config, local users included, to every chassis. A read of 10.69.144.139 and .153 (2026-10-19) shows why the removal must be saved too: once their VC split, each kept the user table it had been given. On 10.69.144.132 (AOS 8.10.86.R04) `write memory` asks for no confirmation, returns 0, and takes under a second. When it fails, the accounts still stand in the running config: the failure is a warning (in the Cleanup's history, or logged), not a reason to make them again.
- **What gets saved with them.** `write memory` saves whatever the user changed in the running config at that moment, into `working/`. That is acceptable: the Switch is theirs while they hold it, and the Cleanup replaces `working/` from `init/` at Release (ADR 0006). A Snapshot then holds those changes too. A Restore syncs the accounts before it writes the Snapshot's config into `working/`, so the save doesn't overwrite it.
- **A slave's refusal is not a failure.** When a slave refuses an account to create, BLab reads `show virtual-chassis topology` on it and looks for its master by MAC among the Switches reserved into the same Project, or by the same holder. Once BLab has made the user's account on that master (its own row is created, with the user's latest Switch password), the slave's `SwitchAccount` row is marked created, with the master's IP in `vc_master`. Until then the slave's row waits, with an error that says so, and is retried like any other. My lab shows it as ready, made on that master. Otherwise the row keeps an error that says why, and is retried as before. An account to remove that a slave refuses counts as removed: the master's own sync removes it from the VC.
- **After a takeover**, the new master already has every account, thanks to the save. If a new member joins afterwards, BLab makes their account on the new master, and the old master, now a slave, points to it.

## Switch details for everyone (#75)

#36 kept a Switch's management IP, console and hardware for the users who may work on it, because anyone who knew the IP could log in as `admin/switch`. On 2026-10-19 the `admin` password changed on every lab Switch, so knowing an IP no longer lets anyone in: only a Switch account does, on a Switch the user may work on. So every user sees every Switch's details again. BLab's texts keep the IP as written, and the UI names a Switch "<model> <IP>" instead of "<model> #<id>". A Tool without an IP is named by its model alone.

## `admin` after a reload (#87)

Each AOS release keeps its own local users table (ADR 0006, #74), so a reload into another release can bring back an older `admin` password: on 10.69.144.132 (2026-10-21), the first Cleanup into 8.11.162.R01 left `admin` taking only `Switch@123`. BLab still logged in, through the fallbacks of `BLAB_SWITCH_ADMIN_PASSWORDS`, but every lab Switch must have the secret password. So, with Titouan's written agreement (2026-10-21):

- **After every reload BLab starts** (a Cleanup, whether or not it installed a release, a Restore, and a member's AOS install, #49), once the Switch is back and before the Inspection, BLab checks that `admin` takes the first password of `BLAB_SWITCH_ADMIN_PASSWORDS`. If only an older one works, it sets `admin` to the first and runs `write memory`, with onboarding's code (`lab_switch.secure_admin`), and checks that the first password then logs in.
- **It is recorded** in the history of the action: the Cleanup's event, or the Restore's row for that Switch. A failure is only a warning there, never a reason for a Quarantine: BLab still logs in with the older password, and tries again after the next reload.
- **Nowhere else** does BLab change `admin`, but for the Login check below (#92). The password never appears in a history or log line (`user admin password ...`).

## Logins lost to a reload BLab didn't start (#92)

The table a reload brings back is the release's, whoever reloads. On 10.69.144.132 (2026-11-03) `/flash/system/` holds `userTable8` to `userTable11`, one per release train, so a member who upgrades from the CLI from 8.10 to 8.11 and reloads, or a power cut that boots `certified/`'s other release, comes up with that release's users: no Switch accounts, and maybe an `admin` that takes only `switch` or `Switch@123`. BLab's own flow is not the cause: after the reloads it starts it already makes `admin` and the accounts again (#87, #49). Decided with Titouan (2026-11-03):

- **The Login check.** Every 15 minutes, a few Switches per cycle, the Switch worker looks at each Switch in service with a management IP that isn't being Cleaned up, Restored or installed (`api.login_check`). If `admin` takes only an older password, it sets the first of `BLAB_SWITCH_ADMIN_PASSWORDS` with onboarding's code (`lab_switch.secure_admin`, which also runs `write memory`) and makes every Switch account of the Switch again. Otherwise it reads `show user`, and makes again any Switch account BLab made there that is gone. A Switch whose last login in the worker took an older `admin` password (the Sweep's Inspection, say) comes first. One whose AOS refuses `user` commands because it is not ready yet is looked at again after a minute.
- **Not in a history.** The check is logged by the worker, not recorded as a Switch event: there is no action of a user's to attach it to, and a kind of event of its own would need a migration for little.
- **Re-create my account.** For an account lost on its own, My lab offers *Re-create my account* on each Switch the user may work on (`POST switch_accounts/<switch>/recreate/`). It marks the user's `SwitchAccount` row not created, and the Switch worker's account pass makes it within seconds, through the same `sync` as every other account.

## SU allowed on every Switch account (#95)

A Switch account was made with `read-write all` alone, and AOS 8.10 and later then show it with `SU allowed = NO`: its user can't open the Switch's root shell (`su`). Decided with Titouan (2026-11-03): every Switch account gets SU allowed. The Cleanup restores the Switch after the Release, and the Inspection reports whatever SU work leaves behind.

- **The command.** On 10.69.144.132 (AOS 8.11.162.R01, 2026-11-03), `user <name> password '<password>' read-write all su enable` makes the account with `SU allowed = YES` (`allow-su` and `superuser` are refused as `ERROR: Invalid entry`). A `user` command that doesn't say keeps SU as it was, so BLab always says: `su enable`, or `su disable` for an account that must not have it (`lab_switch.account_command(name, password, su)`; #91's read-only accounts will pass `su=False`). A release without SU (show user doesn't print it before 8.10) should refuse the `su` word as 8.11 refuses `allow-su`, with `ERROR: Invalid entry: "su"` (not checked on such a release): BLab then runs the command without it.
- **Accounts made before.** No migration: the Login check (#92) also makes again, within its 15 minutes, any Switch account BLab made that `show user` lists with `SU allowed = NO`. A Switch whose release doesn't say is left alone. #91's read-only accounts must be left out of this check. Making an account again removes it first (AOS refuses its current password), but on 132 an SSH session open on it carries on.
- **The Inspection.** It still reports SU allowed for any local user but `admin`, except the Switch's accounts: on a reserved Switch BLab gave them SU, and on one nobody holds an account left is already a reason of its own.
