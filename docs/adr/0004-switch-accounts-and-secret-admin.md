# Users get their own Switch accounts; `admin` stays secret

The lab got messy because anyone could log in to any Switch with the default `admin/switch`, so nobody reserved, and nobody could be held to cleaning up. We now keep the lab Switches' `admin` password secret, known only to BLab and the admins, and stored in deployment secrets rather than in the code. Users reach a Switch only through a **Switch account**: a local login named after them, with a random password. BLab creates it on Reserve for the holder and for each user the Topology is shared with, and removes it at Release before the Cleanup. Backbones keep their current credentials for now.

## Considered options

- **RADIUS/TACACS behind BLab.** Rejected: too much infrastructure for a lab, and BLab's own access would depend on it.
- **BLab sets a new `admin` password for each Reservation and gives it to the holder.** Rejected: a holder who changes it locks BLab out, so the Switch can no longer be Cleaned up, and the command log shows `admin` instead of a person.

## Consequences

- Cleanup doesn't touch the local user table, because it lives outside `working/`. Removing Switch accounts is a separate step of Release, and an Inspection fails if a Switch account is still there once the Switch isn't reserved.
- A holder can still lock BLab out by changing `admin` or removing SSH authentication. The Inspection after Cleanup then fails, the Switch is Quarantined in their name, and an admin recovers it at the console. There is no console server.
- The `admin` password changes on the devices only after BLab has shipped Switch accounts, so holders always have a way in.
- Scripts that hard-code `admin/switch` stop working on lab Switches.

## How it is done (#21)

- **BLab's login.** BLab logs in to lab Switches as `admin`, trying each password of `BLAB_SWITCH_ADMIN_PASSWORDS` in `.env` (comma-separated, default `switch,Switch@123`, the two passwords the lab uses today) and starting with the one that last worked on that Switch. Changing `admin` is then: put the new password first in both `.env` files, change it on the devices at any pace, and drop the old ones once every Switch has it. BLab never sends a command that changes `admin`. Backbones log in with `BLAB_BACKBONE_USERNAME`/`BLAB_BACKBONE_PASSWORD` (default `admin`/`switch`).
- **The AOS commands**, checked on an OS6900 with AOS 8.9.107.R02: `user <name> password "<password>" read-write all` creates the account with full privileges and SSH allowed, or resets the password of an existing one; `no user <name>` removes it. AOS answers both with exit status 0 even when it refuses them, printing `ERROR: ...` (such as `ERROR: Unknown user`, or `ERROR: Command not allowed on slave` on a VC member), so BLab reads the output. The user table is not in `vcboot.cfg`, so it isn't in the config an Inspection compares with init.
- **Names.** A Switch account is named after the BLab username when AOS takes it as is (1 to 63 ASCII letters, digits and `._@+-`, case-sensitive). Otherwise, and for a username that is `admin` or `default` in any case or of the form `blab-<number>`, it is `blab-<user id>`. So two users never share a name and nobody gets `admin`. BLab shows the name next to the password.
- **Passwords** are random, 16 characters, and meet AOS's default policy (upper and lower case, digit, symbol, not containing the name; no `!`, which AOS refuses). BLab stores each one in its `SwitchAccount` row so it can show it, but only to that account's user (`GET switch_accounts/`); the admin site doesn't show it. It is not encrypted: the two stages have different secret keys, and it only opens a lab Switch while the user may work on it anyway.
- **Failures never block.** Reserve, Share and Unshare create or remove the accounts at once; the Release's Cleanup removes them before the reload. If a Switch can't be reached or refuses, the Reservation, Share or Release still stands, the row keeps the error, and the Switch worker retries every few minutes. It also creates the accounts of Reservations and Shares made through code that doesn't know about them (production before this change). Rows are saved before BLab talks to the Switch and no lock is held meanwhile, so a crash leaves a row the worker finishes.
- **The account sync has its own lock** (`SWITCH_ACCOUNTS_LOCK`), apart from the Cleanup lock of ADR 0005, so it runs whichever stage holds the Cleanup lock, including one whose older code knows nothing of Switch accounts.
- **Until `main` runs this code**, a Release or expiry through production Cleans up the old way: it doesn't remove the accounts first and its Inspection doesn't look for them. Pre-prod's worker removes them on its next pass (retried every few minutes while the Switch reloads), so a released user may keep their login for a few minutes, and Reservations made through production get their accounts the same way. This closes once `main` has Switch accounts; until then `admin` keeps working, so nobody is locked out.
- **Inspection.** On a Switch that isn't reserved, a local user named like a `SwitchAccount` row of that Switch is a Switch account left behind and fails the Inspection. Other local users (made by hand, such as `test`) are only a warning, since BLab doesn't know who made them. When all an Inspection after Cleanup finds is accounts left behind, BLab failed to remove them, so the Quarantine names nobody; the worker removes them and a Re-check lifts it.
